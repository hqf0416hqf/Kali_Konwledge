## 一、API、SDK、MCP 与 Skill：从实际连接理解概念

**学习对话整理。** 你的原始疑问是：“我一直不理解像 MCP、SDK、API……”这次用“让终端中的 Codex 读取 Chrome 聊天，再写学习笔记”作为具体例子。

### 1. 为什么需要这些东西

你可以用鼠标查看网页，但程序需要明确的方式才能获得同样的信息。它必须知道：调用哪个操作、传什么参数、得到什么结果，以及失败时如何处理。

随后又有两个问题：开发者是否要从头编写所有连接代码？AI 应用连接多种工具时，是否要分别理解每种工具独有的交流方式？API、SDK 和 MCP 分别帮助解决这些问题。

| 概念 | 全称 | 关注的问题 | 在这次实践中的位置 |
|---|---|---|---|
| API | Application Programming Interface，应用程序编程接口 | 能做什么、怎样调用、返回什么 | Chrome 调试接口提供浏览器能力；工具也有自己的参数约定 |
| SDK | Software Development Kit，软件开发工具包 | 怎样方便地开发、调用和调试 | 开发 MCP 客户端或服务端时可用对应语言的 SDK |
| MCP | Model Context Protocol，模型上下文协议 | AI 应用与外部服务怎样按共同规则交换信息 | Codex 与浏览器连接服务之间的交流 |
| MCP server | 实现 MCP 的服务程序 | 谁实际提供工具或资料 | 本次的 `chrome-devtools-mcp` |
| Skill | 可复用的任务说明与配套资源 | 拿到能力后，按什么流程完成任务 | `web-learning-notes` 指导筛选、整理、去重和日期归档 |

### 2. API：面向程序的使用约定

API 的核心是软件向其他程序开放的能力及其使用规则。API 不只存在于互联网：库函数、系统接口、浏览器接口和网络服务接口都可以是 API。[MDN：API](https://developer.mozilla.org/en-US/docs/Glossary/API)

**整理补充例子，以下是概念示意，不能直接当作已存在的函数运行：**

```python
get_page_text(page_id=4)
```

这条调用约定至少应回答：

1. `page_id` 是整数还是网址？
2. 返回纯文本，还是包含标题、网址、正文的对象？
3. 页面关闭、权限不足或内容尚未加载时，怎样报告失败？

因此，看 API 文档时不要只记函数名。应一起看**参数、返回值、错误和前提条件**。接口规定怎样使用，具体实现负责真正完成操作。

### 3. SDK：把通用开发工作做成可复用的工具

只有接口说明，开发者仍可能要自己编写连接、请求组织、结果解析等代码。SDK 通常把相关库、示例和文档整理成一套开发工具，有时也包含构建或调试工具。

一个 SDK 提供的函数和类，本身也构成 API。所以“API 和 SDK”不是互斥分类：**SDK 是一套开发材料和工具，其中包含可供调用的接口。**

MCP 官方提供多种语言的 SDK，用于开发遵守 MCP 规则的客户端和服务端。具体语言支持与成熟度应以当时文档为准。[MCP 官方 SDK](https://modelcontextprotocol.io/docs/2026-07-28/sdk)

SDK 也不一定都围绕 HTTP。嵌入式开发中的 SDK 可能提供外设访问库、头文件、示例和构建支持。以后阅读 K210 的 SDK 时，可以具体找“有哪些接口”“怎样构建”“示例调用了什么能力”，而不只把 SDK 当成安装包名称。

### 4. MCP：共同的交流规则；server：实际提供服务的程序

MCP 采用 host、client、server 的结构。Host 是组织工具使用的 AI 应用；client 是它连接某个服务的组件；server 是提供工具或资料的程序，既可以在本机运行，也可以在远端运行。[MCP 官方架构](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

把这些角色放入这次实践，可以这样理解：

```text
你提出整理需求
    ↓
Codex：理解任务、组织工具调用、整理结果
    ↓ 内部的 MCP client 按协议交流
chrome-devtools-mcp：提供浏览器工具
    ↓ 调用 Chrome 调试能力
Chrome：返回页面和聊天内容
    ↓
Codex 按 web-learning-notes 的规则整理
    ↓
RAW/2026-10-08.md
```

**SDK 不是这张图中必然多出来的一跳。** 它通常用于开发上述组件，或者作为组件内部使用的库。

在工具调用场景中，可以先认识“列出工具 → 看工具说明和参数 → 发出调用 → 得到结果”这一过程。MCP 的工具发现与调用对应 `tools/list` 和 `tools/call`；服务也可以提供 resources（上下文资料）与 prompts（可复用提示模板）。[MCP 工具与资料概念](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture#primitives)

日常说“安装一个 MCP”，通常是在简称“安装一个实现 MCP 的服务程序”。**协议是规则，server 是实现规则并实际运行的程序。**

### 7. 系统补充与延伸思考

**系统补充：接口与协议的区别。** 接口关注“一个能力如何使用”；协议关注参与者如何交换消息及这些消息是什么意思。一个协议可以规定一组接口，而 SDK 可以帮助实现这些接口。把它们当作不同观察角度，会比强行分成互不相交的几个盒子更准确。

**延伸思考：用四个问题拆解陌生技术名词。** 遇到新工具时，先问：它提供什么能力？谁真正运行和执行？通过什么规则连接？开发或使用时有什么辅助材料？这个方法适合阅读工程文档，但只是理解框架，不能替代对参数和运行条件的核对。

## 二、K210 连接电脑：设备识别、Shell 与访问权限

**网页学习整理 + 对旧笔记的实质补充。** 项目聊天中的关键追问是：“这个怎么看？”“`2>/dev/null` 这个我不知道”“解释 `id -nG` 及其应用场景”。这些问题串起来，正好形成一个可复用的设备排查过程。

已有 [Linux 笔记](../WIKI/CS/tools/Linux/Linux.md) 记录了硬件发现、驱动、设备接口与权限的排查框架；已有 [Shell 笔记](../WIKI/CS/tools/Shell/Shells.md) 涉及解释器、脚本和环境变量。本节补充命令具体含义及证据之间的关系。

### 1. 读懂 `lsusb` 的一行结果

聊天中出现：

```text
Bus 001 Device 015: ID 1a86:55d4 QinHeng Electronics USB Single Serial
```

| 部分 | 含义 | 排查时怎么用 |
|---|---|---|
| `Bus 001` | 所在 USB 总线编号 | 描述设备当前连接位置的一部分 |
| `Device 015` | 本次枚举分配的设备编号 | 重新插拔可能改变，不能把它当永久编号 |
| `1a86:55d4` | 厂商 ID 与产品 ID（VID:PID） | 描述设备类型，通常比本次设备编号稳定；不是唯一序列号 |
| `QinHeng ... USB Single Serial` | USB 通信设备的识别信息 | 电脑可能显示板上通信芯片的信息，而非 K210 名称 |

判断哪一项对应开发板，最直接的证据是**拔掉时消失，插上时出现**。看到 USB 设备只能说明系统发现了它；还不能由此确认串口可以打开，或板上程序已经正常运行。

### 2. `ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null`

```bash
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
```

| 部分 | 作用 |
|---|---|
| `ls` | 列出文件或设备节点 |
| `-l` | 显示类型、权限、属主、属组等详细信息 |
| `/dev/ttyUSB*` | 匹配名称以 `ttyUSB` 开头的路径 |
| `/dev/ttyACM*` | 匹配名称以 `ttyACM` 开头的路径 |
| `2>/dev/null` | 将标准错误重定向到丢弃内容的特殊设备 |

**系统补充：通配符通常先由 shell 展开。** `ls` 往往接收到的是已经展开的文件名。Bash 默认在没有匹配时保留原模式，随后 `ls` 可能报告文件不存在；其他 shell 或不同设置可能采用不同处理方式。

特别是 zsh 的 `NOMATCH` 行为会在模式没有匹配时报告错误，命令可能尚未执行。因此，不能把“加上 `2>/dev/null` 就总能隐藏无匹配问题”当成适用于所有 shell 的规则。[zsh：NOMATCH 与通配符选项](https://zsh.sourceforge.io/Doc/Release/Options.html#Expansion-and-Globbing)

### 3. 为什么 `2>` 表示错误输出

程序常用的三个标准通道是：

| 编号 | 名称 | 典型用途 |
|---|---|---|
| 0 | stdin，标准输入 | 程序读取输入 |
| 1 | stdout，标准输出 | 输出查询结果等正常数据 |
| 2 | stderr，标准错误 | 输出报错和诊断信息 |

这些编号是文件描述符。`>` 指定输出去向；省略编号时通常处理标准输出，写成 `2>` 则指定标准错误。[GNU Bash：重定向](https://www.gnu.org/s/bash/manual/html_node/Redirections.html)

```bash
# 概念示例：三条命令分别执行，假设 demo-command 是某个实际程序
demo-command > result.txt
demo-command 2> error.txt
demo-command 2>/dev/null
```

第一条把正常输出写入文件，第二条把错误输出写入文件，第三条丢弃错误输出。这些例子没有在本次执行。

**使用边界：** `2>/dev/null` 不会修复错误，也不会保证命令成功。首次排查设备或权限问题时，应保留错误信息；已经知道某类设备不存在、只想让列表简洁时，才考虑隐藏预期的诊断。

### 4. 读懂 `/dev/ttyACM0` 的权限

项目聊天中，你给出的结果是：

```text
crw-rw---- 1 root dialout 166, 0 10月 8 00:34 /dev/ttyACM0
```

前面的字符可以拆成：

```text
c | rw- | rw- | ---
类型  属主   属组   其他用户
```

- `c`：字符设备。这类节点提供面向设备驱动的访问入口，并不是普通文本文件。
- 属主 `root` 的 `rw-`：允许读和写。
- 属组 `dialout` 的 `rw-`：该组成员允许读和写。
- 其他用户的 `---`：没有这里列出的读写权限。
- `166, 0`：设备主、次编号，用于内核识别设备，不是文件大小。
- `/dev/ttyACM0`：应用打开的设备路径。本次应使用实际发现的路径，而不根据别人教程固定选 `ttyUSB0`。

设备命名可能在重新插拔或接入多块板子后改变。不同命名也不能单独证明具体芯片型号。这里最关键的是“已找到接口”和“它允许谁访问”。

### 5. `id -nG`：把设备权限与当前身份对应起来

```bash
id -nG
```

`id` 查看用户身份；大写 `-G` 输出全部组 ID；`-n` 将相关数字 ID 显示为组名。因此，`id -nG` 与 `id -G -n` 等价。小写 `-g` 只选择主组，不能与大写混用理解。本次还查阅了本机 `id --help` 核对选项。[GNU Coreutils：id](https://www.gnu.org/software/coreutils/manual/coreutils.pdf)

你的输出包含 `dialout`，与设备属组对应：

```text
设备允许 dialout 组读写
             +
当前身份的组列表包含 dialout
             ↓
按已展示的 Unix 权限，具备读写该设备的条件
```

这里说明的是基础权限条件。实际打开还可能受到其他访问规则或端口占用等因素影响，最终要结合应用运行结果。

**常见组名的用途：** `adm` 常与部分日志读取有关，`dialout` 常用于串口，`sudo` 与配置允许的管理员操作有关，`lpadmin` 与打印机管理有关。组名本身不是权限的全部定义，具体仍取决于设备、文件和系统配置；用户名或组名叫 `kali` 也不能证明当前发行版一定是 Kali Linux。

**系统补充：** 不带用户名的 `id` 反映当前进程身份。调整组成员后，已有会话可能仍保留原来的组列表；应重新检查实际启动 IDE 的会话是否获得新组，而不是只看账户数据库。[GNU Coreutils：groups 与会话组信息](https://www.gnu.org/s/coreutils/manual/html_node/groups-invocation.html)

### 6. 把排查动作组织成证据链

```text
物理连接和供电
    ↓
lsusb：系统是否发现 USB 设备
    ↓
/dev：是否产生可供应用使用的设备接口
    ↓
ls -l + id -nG：设备访问规则与当前身份是否匹配
    ↓
IDE：能否打开接口并与板子通信
    ↓
相机示例：具体应用链路能否运行
```

**延伸思考：** 每一步回答的问题都更具体。后一步失败时，回查最近没有证据支撑的那一层，比立即重装驱动或使用管理员身份更有助于定位原因。这个方法适用于开发板、USB 串口和不少外设；不同设备的应用接口可能不同。

## 三、从相机采图到 AprilTag 检测与画面偏差

**网页学习整理，偏差计算为系统补充。** 你报告相机示例成功后，网页给出了下一步：检测一个测试 AprilTag，打印编号与中心位置，为后续小车控制准备观测数据。

### 1. AprilTag 解决什么问题

AprilTag 是一种视觉标记系统。相机检测标记后可以取得它的 ID 和图像位置，并在具备相应信息与算法时估计姿态。它适合机器人需要持续识别指定目标的场景。[AprilRobotics 官方项目](https://github.com/AprilRobotics/apriltag)

**家族（family）与 ID 要一起理解。** 家族规定一组标签的编码设计，ID 是该家族中的编号。网页建议用 `tag36h11`、ID 0 作测试，这只是实验选择；比赛实际采用的家族和 ID 尚未确认。

虽然项目名是 AutoQR-Rover，本段实际讨论的是 AprilTag。QR 码与 AprilTag 的设计目标不同，后续代码和比赛标记应按真实类型匹配，不能因外观相似就互换。[OpenMV：QR 码与 AprilTag](https://docs.openmv.io/dev/zh_CN/openmvcam/tutorial/image/decoding/qr-apriltag.html)

### 2. 网页给出的检测循环

以下是**网页示例整理，尚无本次板端运行结果**。它依赖已有的摄像头、屏幕初始化代码，以及实际固件提供的相应接口。

```python
import image

while True:
    img = sensor.snapshot()
    tags = img.find_apriltags(families=image.TAG36H11)

    for tag in tags:
        img.draw_rectangle(tag.rect())
        img.draw_cross(tag.cx(), tag.cy())
        print("ID:", tag.id(), "中心:", tag.cx(), tag.cy())

    lcd.display(img)  # 仅在原来已跑通的显示代码使用这个接口时保留
```

理解顺序是“采一帧 → 返回该帧中的检测结果列表 → 逐个画框、标中心、输出结果”。关键结果分别是标签编号、横向像素位置和纵向像素位置。

**兼容性边界：** 核查的 Kendryte CanMV 源码包含 AprilTag 检测和 `TAG36H11` 分支，但这只证明相关源码提供了实现，不能证明你烧录的具体固件已经启用。不同版本也可能把结果字段设计成属性或方法；本例沿用网页针对当前项目给出的 `tag.cx()` 等写法，不能直接套用其他版本的新文档。[CanMV 检测源码](https://github.com/kendryte/canmv/blob/main/components/micropython/port/src/omv/img/apriltag.c)

若运行报错，下一步应记录固件版本、完整报错和实际代码，再判断是功能缺失还是接口形式不同。

### 3. 像素中心与图像偏差

**系统补充。** 设图像宽、高为 `W`、`H`，采用左上角为原点、向右与向下递增的像素坐标。标签中心为 `u = tag.cx()`、`v = tag.cy()`。

为了控制对齐，可以先选择参考中心 `(W/2, H/2)`，定义：

```text
e_x = u - W/2
e_y = v - H/2
```

`e_x`、`e_y` 的单位都是像素。若画面为 320 × 240，并以 `(160, 120)` 为参考：

```text
标签中心 (200, 120)
e_x = 200 - 160 = +40 像素
e_y = 120 - 120 = 0 像素
```

这个结果表示标签在参考中心右侧。它还不能直接说明目标距离相机 40 厘米，或小车应该转动 40 度。

**精度边界：** 若严格按从 0 开始的像素索引计算两端的几何中点，是 `((W-1)/2, (H-1)/2)`。而标定得到的相机主点又可能偏离图像几何中心。初步对齐可明确选用一个参考中心；后续几何估计应使用对应的相机参数，不能混用这些概念。

### 4. 从图像位置走向控制，还缺什么

可将后续系统分成：

```text
相机图像 → 标签检测 → 筛选目标 ID → 图像偏差 → 控制计算 → 执行器
```

目前建议先验证观测这一端：标签能否检测、ID 是否正确、向右移动时横坐标是否增大、向下移动时纵坐标是否增大。

**系统补充：** 若需要实际位置和姿态，通常还需要相机内参、标记的物理尺寸和相应估计方法。AprilTag 官方的姿态估计示例明确使用标签尺寸与焦距、主点参数；单独一个像素中心不足以得到真实距离。[AprilTag：姿态估计](https://github.com/AprilRobotics/apriltag#pose-estimation)

**延伸思考：** 对当前项目，先把“ID + 中心坐标”稳定输出，再尝试控制，能把视觉失败和控制失败分开排查。未来还需要考虑多个标签如何选目标、短暂漏检如何处理、坐标方向与车体方向如何对应。这些是后续设计问题，尚未在此次实践中验证。
