## 一、Git：先建立对象与引用的关系，再理解整合历史

本次实际卡点是：“哈希是什么意思，历史不变是什么意思，HEAD 本质是什么？”因此这里补足对象关系，不重复此前工作区／暂存区状态列的课程。已有笔记见 [Git](../WIKI/CS/tools/Git/Git.md)。

### 1. 一个提交记录了什么

可以把 commit 理解为一次版本记录，但它不是给整个项目另建一个普通文件夹。对象间的关系如下：

```text
HEAD ──通常指向──> refs/heads/main ──指向──> commit C
                                              ├─ tree：该版本的目录结构
                                              │   └─ blob：文件内容
                                              ├─ parent：上一个提交 B
                                              └─ 作者、提交者、说明等
```

Tree 将名称、模式与内容对象或子目录关联起来；blob 保存文件内容。沿 commit 的 parent 向前追溯，才得到历史。分支名是可移动的引用，提交后通常移动到新提交。多个分支可以指向同一个提交，创建分支也不等于复制一个项目目录。

Hash 是由对象内容计算出的标识，常见日志只显示足以区分对象的短前缀。它不只是对当前代码文本算一次哈希：commit 的父提交、元数据等也参与对象内容。因此两个提交的代码可以相同，提交标识仍不同。

普通情况下 `HEAD → 分支 → 提交`；检出某个具体提交时，可以是 `HEAD → 提交`，称为 detached HEAD。不能把 HEAD 永远等同于“最新提交”，它表达的是当前检出位置。[Git 官方术语表](https://git-scm.com/docs/gitglossary)

### 2. merge 与 rebase 改变了哪部分

下面所有线条按“旧版本到新版本”画；提交对象内部保存的 parent 引用指向相反方向的旧提交。

```text
起点：       A──B        main
             ╲
              C         feature，当前所在分支

merge 后：   A──B────┐   main 仍在 B
             ╲      │
              C─────M   feature 在 M；M 的父提交是 C、B

rebase 后：  A──B──C'    main 在 B，feature 在 C'
```

- 在上面的分叉情形执行 `git merge main`，会把两边修改整合进 M；A、B、C 这些原提交对象保持不变。这就是这里的“保留历史”，并不意味着工作区文件不会变化。
- 从同一起点执行 `git rebase main`，会把 C 引入的修改重新应用到 B 上，产生 C'。父提交从 A 变成 B，提交身份随之改变；feature 的可达历史也改变。旧 C 并非立刻被物理删除。
- 快进合并是另一种情形：当前分支顶端是目标提交的祖先时，通常只需移动引用，不产生合并提交。不能记成“merge 必定创建 M”。

以上是普通分叉例子。rebase 可能跳过已包含的补丁或成为无操作，不能推成“每次 rebase 都必定生成同样数量的新提交”。共享历史的处理遵循协作约定；这份笔记没有在知识库执行合并、变基或推送。[git merge](https://git-scm.com/docs/git-merge)、[git rebase](https://git-scm.com/docs/git-rebase)

**整理补充：用只读命令把图和仓库对应起来。** 以下作为复习命令，未在本次做教学实验：

```bash
git log --oneline --graph --all --decorate
git rev-parse HEAD
git symbolic-ref -q HEAD
git cat-file -p HEAD
```

依次观察历史图与引用标记、当前提交标识、HEAD 是否指向分支，以及 commit 中的 tree／parent 字段。第三条在 detached HEAD 下可能不输出分支引用；不要把这自动判断为仓库损坏。

## 二、概率：指数分布的推导与“已经等了多久”

已有 [概率笔记](../WIKI/Math/Probability‑And‑Statistics/Probability.md) 记过均匀、指数分布的名称和公式。本次实质新增是推导和条件解释。

### 1. 均匀分布只补充易混点

若 $X\sim U(a,b)$，$a<b$，均匀指的是支持区间内**等长度区间具有相同概率**。密度为 $1/(b-a)$，单点概率仍是 $P(X=x)=0$。密度可以大于 1，受限制的是积分所得概率。旧笔记中“每点等可能”的表述应按这一含义理解；本次只在 RAW 解释，没有修改原条目。

对 $a\le c<d\le b$，有 $P(c\le X\le d)=(d-c)/(b-a)$，而 $E[X]=(a+b)/2$、$\operatorname{Var}(X)=(b-a)^2/12$。公交等待服从均匀分布，需要固定班距与相对发车周期均匀到站等前提。

### 2. 从“零次到达”得到“还没等到”

设事件满足速率恒定为 $\lambda>0$ 的齐次泊松过程条件，$N(t)$ 表示 $t$ 时间内的到达次数，$T$ 表示第一次到达的等待时间。参数单位要匹配：$\lambda$ 是每单位时间的平均次数，$\lambda t$ 才是区间内平均次数。

关键事件等价关系是：

$$
\{T>t\}=\{N(t)=0\},\qquad
P(T>t)=P(N(t)=0)=e^{-\lambda t},\quad t\ge0.
$$

取补集得到分布函数，再求导得到密度：

$$
F_T(t)=1-e^{-\lambda t},\qquad
f_T(t)=\lambda e^{-\lambda t}\quad(t\ge0).
$$

$t<0$ 时两者均为 0。这里采用速率参数，写作 $T\sim\operatorname{Exp}(\lambda)$；速率越大，平均等待越短。

“恒定到达速率”不表示首次到达时间的密度恒定。要第一次在较晚时刻发生，必须前面一直没有发生，这一条件的概率会随时间下降。对 $0\le a<b$，区间概率为 $e^{-\lambda a}-e^{-\lambda b}$。

### 3. 均值和方差为什么是倒数形式

分部积分给出：

$$
E[T]=\int_0^\infty t\lambda e^{-\lambda t}\,dt
=[-te^{-\lambda t}]_0^\infty+\int_0^\infty e^{-\lambda t}\,dt
=\frac1\lambda.
$$

同理，边界项消失，

$$
E[T^2]=2\int_0^\infty te^{-\lambda t}\,dt
=\frac2\lambda E[T]=\frac2{\lambda^2},\qquad
\operatorname{Var}(T)=\frac1{\lambda^2}.
$$

例如 $\lambda=2/\text{分钟}$ 时，平均等待 $0.5$ 分钟，$P(T>0.5)=e^{-1}$。注意均值的单位是时间，方差的单位是时间平方。

### 4. 无记忆性说的是剩余时间

对 $s,t\ge0$，

$$
P(T>s+t\mid T>s)
=\frac{e^{-\lambda(s+t)}}{e^{-\lambda s}}
=e^{-\lambda t}=P(T>t).
$$

已等 $s$ 仍未发生时，剩余等待时间的分布不变；总等待时间的条件均值则为 $E[T\mid T>s]=s+1/\lambda$。固定班距的公交车、明显老化的部件，不能仅因研究“等待／寿命”就套用指数分布。

系统联系：把时间切成独立小段，令每段事件概率为 $\lambda t/n$，则 $(1-\lambda t/n)^n\to e^{-\lambda t}$，连接了几何等待与连续时间等待。这是极限模型，不是说真实过程每段概率都严格等于速率乘时长。[指数分布教材：定义与无记忆性](https://www.probabilitycourse.com/chapter4/4_2_2_exponential.php)

用户表示均匀分布简单并主动要求指数分布证明，但没有提交所给习题的答案；记录为“已讨论，待独立检验”。

## 三、K210：优化外层代码前，先找耗时在哪里

先前的 [视觉与嵌入式笔记](2026-10-12.md) 已介绍 AprilTag、PnP、KPU。本次新增问题是：“换 C/C++ 固件会不会大幅加速？用 NPU 会不会更准？”

### 1. 语言、库、算法、硬件是四个维度

| 维度 | 本次问题中的例子 | 能说明什么 |
| --- | --- | --- |
| 语言 | MicroPython、C/C++ | 外层程序如何编写和执行 |
| 库 | 板载 image、AprilTag、OpenCV | 提供哪些接口与实现 |
| 算法 | 标签解码、角点定位、神经网络 | 怎样得到检测和定位结果 |
| 硬件 | CPU、KPU | 哪类运算由哪个计算单元承担 |

MaixPy-v1 源码的 Python 图像接口调用原生 `imlib_find_apriltags`，所以“用 Python 调用”不等于“检测算法全部由 Python 逐像素解释执行”。主要时间若在原生检测中，改写调用层的收益就有限。[MaixPy-v1 图像接口源码](https://raw.githubusercontent.com/sipeed/MaixPy-v1/master/components/micropython/port/src/omv/py/py_image.c)

**系统补充：串行耗时的上限估算。** 假设原耗时中可优化部分占比为 $p$，该部分加速 $s$ 倍，总加速比是

$$
S=\frac1{(1-p)+p/s}.
$$

例如检测 90 ms、Python 逻辑 10 ms，将后者降为 1 ms，总耗时是 91 ms，总加速约 1.10 倍；即使把它消除，也最多约 1.11 倍。这是算例，不是板子实测，也未包含流水线并行的情况。

MaixPy-v1 官方仓库支持作为 C SDK 使用，也给出了通过 KPU 加载模型和推理的例子。二者是不同选择：C/C++ 不会自动把普通图像算法转换成 KPU 网络运算。完整 OpenCV 的移植还涉及内存、依赖和硬件适配；不能因为支持 C++ 就认定可直接使用桌面 OpenCV。[MaixPy-v1 官方仓库](https://github.com/sipeed/MaixPy-v1)

### 2. “准确率”要拆成可测指标

| 指标 | 检查方式 |
| --- | --- |
| 检出率 | 标签存在的帧中，有多少帧检出目标 |
| 身份正确性 | 是否把家族和 ID 解码正确；另统计误识别 |
| 几何精度 | 相对已知距离／姿态，测量偏差多大、抖动多大 |
| 时间性能 | 分别记录采图、检测、显示、通信耗时，以及总延迟 |

普通目标检测网络输出的包围框不等于标签四个真实角点，也不自动完成编码校验。针对既定人工标签，可以先建立专用 AprilTag 算法的基线，再用同一批图像比较其他方法。

本次方案讨论的重点是：先改进成像与标定，再检查角点、尺寸和位姿质量。AprilTag 官方库是独立 C 库；官方参数说明指出增大检测降采样会以检测距离为代价换速度。标签尺寸应对应检测角点之间的边界，不能把纸张外白边算入。[AprilTag 官方实现与参数说明](https://github.com/AprilRobotics/apriltag)

这里不重写之前的 PnP 推导。没有真实测试数据，不能断言换语言或引入网络后精度一定提高；网页给出的实验建议也不代表已经完成。

## 四、STM32：从引脚功能理解到双板可验收实验

### 1. 普通输入、业务按钮、复位机制不能混为一谈

固件是软件；GPIO、UART、定时器、看门狗是芯片内的硬件模块。固件通过寄存器配置它们，引脚只能切换到芯片和封装实际支持的功能。

| 表达 | 实际含义 |
| --- | --- |
| “启动按钮” | 普通 GPIO 输入，由程序赋予启动任务的业务含义 |
| “按键让程序复位” | GPIO 检测按下后，程序执行软件复位 |
| 硬件复位按钮 | 连接专用 NRST 复位线路 |
| 看门狗复位 | 内部计时监控超时后触发复位，并非任意 GPIO 的一种模式 |

STM32F103 的数据手册分别列出 NRST、引脚复用和看门狗模块。理解“功能可配置”时要同时检查硬件边界。[STM32F103x8/xB 数据手册](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)

### 2. ST-Link 到手之后，先验证通信与判断

用户新反馈是 ST-Link 已购买，随后问能否连接 STM32 和 K210。ST-Link 承担下载／调试，电机驱动电路承担功率输出；控制电机的逻辑计算和给电机供电是两件事。

对现有小车电机，GPIO 不应直接作为电机供电端。缺少驱动板仍可做“视觉 → 通信 → 判断”的联动：

1. 自己编译下载点灯程序，确认 MCU 运行。
2. 用断点观察变量，确认调试链路。
3. K210 交替发送字符 `'1'`、`'0'`，STM32 接收后切换 LED。
4. 换成“目标标签出现／消失”控制 LED。
5. 传送位置数据，在 STM32 中观察转向、停车等控制变量。

步骤是网页提出的待做实验；当前没有完成点灯、接收或控制变量变化的结果。

初始单向 UART 实验中，K210 已配置的 TX 接 STM32F103C8T6 的 PA10（USART1_RX，默认未重映射），两板共地；需要回传时，PA9（USART1_TX）再接 K210 的 RX。K210 排针须匹配具体板卡的 FPIOA 配置，双方波特率与数据格式一致，电平需匹配，不能把 5V 电源端当 UART 信号。网页建议各板独立正常供电、先不互接电源轨。[STM32 引脚表，PA9/PA10](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)

## 五、存储系统：本次增加 Cache 的性能模型

SRAM／DRAM／Flash 分类和 MMU／TLB 基本区分已有记录，本次只补充层次结构和 Cache 的核心机制。虚拟内存旧内容见 [10 月 12 日笔记](2026-10-12.md)。

Cache 用少量高速存储保存近期可能用到的指令／数据。时间局部性指近期访问可能再次发生；空间局部性指相邻地址常被连续访问。缓存按行搬运，因此顺序数组访问可以复用一次载入的相邻元素。假设行长 64 B、元素 4 B，则一行容纳 16 个元素；这是示例参数，不是所有平台的固定规格。

### 1. 平均访问时间

$$
\operatorname{AMAT}=T_{\mathrm{hit}}+r_{\mathrm{miss}}\,P_{\mathrm{miss}}.
$$

$T_{\mathrm{hit}}$ 是访问该级缓存的基础时间，$r_{\mathrm{miss}}$ 是缺失率，$P_{\mathrm{miss}}$ 是缺失后**额外**代价。命中时间 1 ns、缺失率 5%、额外代价 50 ns 时，平均为 $1+0.05\times50=3.5$ ns。若题目给的是“缺失总耗时”，应换算成额外代价或改用加权平均，避免重复计时。

### 2. 地址怎样决定放在哪一行

直接映射只允许放入一个指定位置；全相联允许放到任意行；组相联先确定组，再在组内匹配。常见组相联模型把地址分为 Tag／Index／Offset，分别用于身份匹配、选组和定位行内字节。

**整理补充算例：** 字节寻址，缓存数据容量 4 KiB、行长 64 B、4 路组相联，组数为 $4096/(64\times4)=16$。因此 Offset 为 6 位，Index 为 4 位；若采用 32 位地址，则 Tag 为 22 位。容量这里不含标签等元数据。

Cache 的替换策略、写回／写直达与写缺失分配仅在网页中概览，尚未深入做题。不能把这次完整讲解记成已经掌握存储系统；网页的 `lscpu -C`、`free -h`、`getconf PAGE_SIZE` 等实验也没有取得执行结果。

## 六、C++ / C# 与交互式 Markdown

### 1. 编译执行与资源释放是不同问题

本次 C++ / C# 对比补充了两个维度：C++ 通常编译成本机代码；C# 常见流程是生成 CIL，再由 .NET 的 JIT 编译为机器码。因此“依赖运行时”不能简单理解为“逐句解释执行”，也不能仅凭语言名字判断最终性能。[Microsoft：托管执行过程](https://learn.microsoft.com/en-us/dotnet/standard/managed-execution-process)

资源管理方面，C++ RAII 将资源生命周期绑定到对象；C# 的 GC 主要解决托管内存回收，不保证某个作用域结束时立即回收对象。需要及时释放文件等资源时，常用 `IDisposable` 和 `using`，在离开规定作用域时调用 `Dispose`。这补充了之前的 RAII 讨论，不等于本次已练习 C#。[Microsoft：using 语句](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/using)

同一窗口后半还询问 NX／NUC 和 RoboMaster 2027 规则。保留“上位机计算平台与 MCU 分工”这一问题线索；网页自认未核实指定日期的正式规则全文，本次也未审查官方完整规则，所以不将其规则改动表、协议或功耗结论归档为已确认事实。

### 2. Markdown 的交互由打开它的环境决定

链接、目录跳转、折叠问答和任务勾选的支持程度取决于渲染器。`<details>` / `<summary>` 可以表达展开内容，但 `.md` 文件包含 HTML 不等于允许执行任意 JavaScript。运行代码需要 Notebook 等执行环境，滑块图像需要交互组件或嵌入网页支持。[MDN：details 折叠元素](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details)
