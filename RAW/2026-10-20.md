## 一、STM32：沿着一条时钟链理解各个部件

学习对话整理：本次的集中疑问是“RTC 和 TIM 有什么区别”“SYSCLK 是什么”“PLL 与预分频器如何工作”，以及它们和 OS 定时中断的关系。此前 [10 月 17 日记录](2026-10-17.md) 主要讨论 GPIO 业务功能、复位和双板通信，这里补充内部时钟与计数机制。

### 1. 先确定每个名字属于哪一层

| 层次 | 对象 | 负责什么 |
| --- | --- | --- |
| 时钟来源 | HSE、HSI、LSE、LSI | 提供周期信号；分别涉及外部／内部、高速／低速时钟来源 |
| 频率生成与选择 | PLL、时钟选择器 | 从可用来源选择时钟，或产生所需频率 |
| 主时钟与总线时钟 | SYSCLK、HCLK、PCLK1、PCLK2 | 确定 CPU、总线和相关外设的工作节拍 |
| 定时器内部 | PSC、CNT、ARR、CCR | 分频、保存计数、确定周期、比较计数值 |
| 事件处理 | 中断控制器、CPU、软件处理程序 | 接收请求并执行处理逻辑 |

SYSCLK 是选定的系统时钟信号，不是一颗专门负责计数的“SYSCLK 芯片”。AHB/APB 是总线体系；HCLK/PCLK 是相关时钟，不能把总线仅理解成几条送时钟的导线。

**两个都叫“预分频器”的部件必须分开：** RCC 中的分频配置影响总线与外设时钟；TIM 的 PSC 位于某个定时器内部，继续把该定时器输入时钟分频。改变 TIM2 的 PSC，不等于改变 CPU 或整个 APB1 的时钟。

### 2. 一条可以手算的链：8 MHz 到 1 ms

假设 STM32F103 使用 8 MHz HSE，PLL 倍频 9 倍，AHB 不分频，APB1 二分频。以下是教学配置，未读取实际开发板寄存器。

```text
HSE 8 MHz → PLL ×9 → SYSCLK 72 MHz
                          ↓ AHB ÷1
                       HCLK 72 MHz
                          ↓ APB1 ÷2
                       PCLK1 36 MHz
                          ↓ F103 的定时器时钟规则
                       TIM2CLK 72 MHz
                          ↓ TIM2 的 PSC=71，即 ÷72
                       CNT 计数频率 1 MHz
                          ↓ ARR=999，循环包含 1000 个计数周期
                       更新周期 1 ms
```

F103 的 APB 定时器时钟规则：APB 预分频系数为 1 时，定时器时钟等于对应 PCLK；否则等于对应 PCLK 的两倍。本例 PCLK1 为 36 MHz，TIM2 输入时钟仍为 72 MHz。这是特定系列的硬件规则，换 MCU 时应重新查看时钟树。[ST RM0008：RCC 时钟说明](https://www.st.com/resource/de/reference_manual/cd00171190.pdf)

在普通内部时钟、向上计数模型中，设 $f_{TIM}$ 为定时器输入频率，则

$$
f_{CNT}=\frac{f_{TIM}}{PSC+1},\qquad
T_{update}=\frac{(PSC+1)(ARR+1)}{f_{TIM}}.
$$

其中 PSC、ARR 是写入寄存器的数值；CNT 保存当前计数值。计数循环为 $0,1,\ldots,ARR$，共有 $ARR+1$ 个状态。取 $f_{TIM}=72\times10^6\ \mathrm{Hz}$、$PSC=71$、$ARR=999$：

$$
f_{CNT}=10^6\ \mathrm{Hz},\qquad
T_{update}=\frac{72\times1000}{72\times10^6}=10^{-3}\ \mathrm{s}.
$$

**边界：** 这是稳定运行、普通溢出更新的计算模型，不直接覆盖中心对齐、外部计数、重复计数等配置。更新事件不等于 CPU 一定进入中断；还需要相应中断使能、控制器配置及 CPU 允许响应。寄存器预装载和首次更新时序也不能单靠这条公式判断。

### 3. PLL 和数字分频器为何不同

数字分频器可以通过触发器与计数逻辑实现。例如每四个输入周期形成一个输出周期，频率就变为原来的四分之一；不需要 CPU 写循环替硬件计数。

PLL（锁相环）的概念模型是反馈控制：比较参考信号与反馈信号的相位关系，调节内部振荡器，再把输出分频送回比较端。锁定时，若反馈分频为 $N$，可以形成 $f_{out}=Nf_{ref}$ 的关系。这个解释是系统补充的通用模型，不是 F103 内部晶体管电路的完整描述；PLL 也不是把每个输入脉冲机械复制 $N$ 次。

CPU 工作时钟为同步电路提供状态转换的节拍；定时器利用时钟或外部事件计数。72 MHz 对应约 13.89 ns 的时钟周期，**不能推出每条指令都恰好用一个周期完成**。

### 4. 芯片型号帮助确定讨论边界

本次讨论对象是 STM32F103C8T6：Cortex-M3 内核，64 KB Flash、20 KB SRAM，最高 72 MHz；型号中的 C、8、T、6 分别对应 48 引脚、64 KB Flash、LQFP 封装及相应温度等级。物理引脚还包括电源、复位等，不等于全部可作 GPIO；最高频率也不等于上电默认频率。[STM32F103x8/xB 数据手册](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf)

学习对话里对整套 STM32 产品系列的分类只是概览，本次不把旧截图整理成当前完整选型表。

## 二、TIM、RTC 和 PWM：相似的计数机制，不同的用途

### 1. RTC 与 TIM 的区别不在于“谁更准确”

| 对比 | TIM | F103 RTC |
| --- | --- | --- |
| 主要用途 | 周期控制、测量、PWM；能力取决于具体 TIM | 持续计时、闹钟、备份域时间维护 |
| 计数来源 | 内部时钟或符合配置的外部事件 | 选定的 RTC 时钟，经自身预分频 |
| 典型硬件 | PSC、CNT、ARR；有通道的定时器还含捕获比较功能 | 独立预分频和 32 位计数器 |
| 日期表达 | 通常不是为日历设计 | 软件可将计数值换算成日期时间 |
| 主电源关闭后 | 普通 TIM 不能靠 RTC 的备用域继续工作 | 需满足备用供电和相应时钟来源条件 |

RTC 的准确度受时钟源误差等影响，并非只因为叫“实时时钟”就一定更准。F103 RTC 是计数器式设计，不能直接套用其他系列的硬件日历寄存器模型。[ST RM0008：RTC 主特性](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)

### 2. PSC／ARR 管周期，CCR 管比较条件

沿用上一节 1 MHz 计数频率与 ARR=999 的例子，在边沿对齐、向上计数、PWM Mode 1 且高电平有效的配置下，输出可在 $CNT<CCR$ 时有效。

$$
f_{PWM}=\frac{f_{TIM}}{(PSC+1)(ARR+1)},\qquad
D=\frac{CCR}{ARR+1}.
$$

$D$ 为占空比；后一公式限定在上述模式和 $0\le CCR\le ARR+1$、寄存器可表示所需数值的范围内。本例 CCR=250、500、750 分别对应 25%、50%、75%，周期均为 1 ms。换输出极性或 PWM 模式，不能照搬这一解释。

**系统补充：** PWM 频率和占空比是不同控制量。示例 1 kHz 只是为了手算，并不是已经根据电机、驱动器和噪声要求完成的选型；占空比也不能直接等同于实际转速。本次没有验证 PWM 波形、驱动板连接或电机运动。

## 三、从定时中断连接到 OS 调度

用户把 STM32 计数器与操作系统切换程序联系起来，这是本次的实质联系。已有 [Linux 笔记](../WIKI/CS/tools/Linux/Linux.md) 记录了 PCB、执行现场、页表与内核的位置，这里只补足链路和概念边界。

```text
时钟驱动硬件计数
  → 产生定时事件
  → 满足使能条件时发出中断请求
  → CPU 响应并执行中断处理代码
  → OS 根据状态判断是否需要调度
  → 必要时保存／恢复任务上下文
  → 继续执行原任务或另一个任务
```

定时器负责产生事件，调度器是决定任务运行的软件；上下文切换是实际保存、恢复运行状态的机制。它们不能合并为“定时器切换进程”。一次中断可以处理完直接回到原任务；任务也可以因为阻塞等原因让出 CPU，因此任务切换不只由周期中断引起。

结合旧笔记再固定两个边界：

- PCB 是管理任务的数据结构，执行现场是恢复运行所需的状态。PCB 可以保存部分现场或指向其保存位置，但两者不是同义词。
- 切换任务不意味着把原任务全部代码、堆、栈复制到 PCB；需要保存的是相应执行状态，并在需要时切换地址空间相关状态。

网页还提及 SysTick、PendSV 与 RTOS，属于后续方向；没有取得相关寄存器实验或用户独立推导。这里不把这些名词扩写成已完成的 RTOS 课程。

## 四、GPIO：高阻态不是第三种固定电压

学习对话整理：输出高、输出低描述主动驱动的结果；High-Z 描述输出端呈现很高阻抗、基本不主动决定节点电压。真实引脚仍有漏电、输入缓冲和保护结构，不能理解成物理上完全断开。

**悬空**描述节点缺少有效的电位约束。一个处于高阻态的输入引脚，如果外部有上拉电阻，节点通常仍可保持高电平；因此高阻态不必然意味着悬空。

系统补充算例：一个输入通过 10 kΩ 电阻上拉到 3.3 V，按钮把节点接地。按钮断开时，上拉提供默认高电平；按下时节点为低电平，电阻中的理想电流约为 $3.3/10000=0.33\ \mathrm{mA}$。这是电路解释，不是已搭建验证的接线方案。上下拉提供默认状态，不能替代负载的功率驱动。[ST STM32F1 HAL 文档：输入与上下拉配置](https://www.st.com/resource/en/user_manual/dm00154093-description-of-stm32f1-hal-and-low-layer-drivers-stmicroelectronics.pdf)

网页另外讨论了焊锡共晶点与晶体谐振。二者分属材料相变和振荡现象，不能因都含“晶”字混为一谈；本次没有取得独立材料资料，不将焊料配比、温度和“最佳焊锡”评价扩写成选购结论。

## 五、网络排错：把“看不懂命令”变成可解释的实验

### 1. 先指出失败发生在哪个阶段

这次用户的关键反馈是：“每次遇到问题毫无思路，解决方案也看不懂。”已有 [Linux CLI 与网络故障排查文档](../WIKI/CS/tools/Linux/Linux_CLI与网络故障排查_从零建立思路_含Codex案例.md) 给出了完整命令地图；本次提炼方法并补入之后的修复证据，不重复复制整份教程。

| 阶段 | 先问的问题 | 不能跳到的结论 |
| --- | --- | --- |
| 命令解析 | Shell 实际找到了哪个入口？ | 同一个命令名永远代表同一份程序 |
| 本地启动 | 程序能执行、能读配置吗？ | 有登录缓存就代表在线认证成功 |
| 网络连接 | 实际进程走什么路径，失败在哪一层？ | 浏览器能用就代表终端也能用 |
| 应用请求 | 哪个接口、哪种身份、返回什么？ | 首页响应可以代表所有业务接口 |
| 最终目标 | 真正需要的功能是否完成？ | 出现窗口或 loading 就是初始化成功 |

每一步都写清：**假设、只改变什么、观察结果、能支持什么、仍排除不了什么。** 这比先搜一长串命令再轮流执行更容易形成可以复用的方法。

### 2. 同一行输出包含不同层次的证据

用户在网页提供的输出是：

```text
HTTP=403 CONNECT=200 TLS=1.562088s TOTAL=2.170753s
```

| 项目 | 能说明什么 |
| --- | --- |
| CONNECT=200 | 代理接受了建立隧道的请求 |
| TLS=1.562088s | 从本次传输开始到握手完成累计约 1.56 秒 |
| HTTP=403 | 被请求的资源返回拒绝响应 |
| TOTAL=2.170753s | 整次传输总计约 2.17 秒 |

**补充纠偏：** 这里的 `TLS` 是输出标签，对应 `time_appconnect`，不是“纯 TLS 握手独占耗时”。代理隧道响应码与最终资源响应码也不是同一层。这个结果既不能证明账号被封，也不能证明实际业务接口正常。[curl 官方手册：write-out 字段](https://curl.se/docs/manpage.html)

### 3. 本次新增的后续结论：前台设置不改变旧后台

网页阶段的已知事实是“两个不同入口／版本，一个失败、另一个可用”。这能提示检查客户端差异，却不足以断言某个版本普遍有缺陷。

随后本地会话与修复报告给出更有区分力的对照：

| 报告记录的实验 | 结果 | 增加的信息 |
| --- | --- | --- |
| 同一版本独立后台，无代理，读取账号 | 约 15.004 秒后出现原始超时 | 可在账号业务层复现 |
| 同一版本、相同账号，独立后台显式使用代理 | 约 1.437 秒读取成功 | 相同凭据和版本能够完成请求 |
| 只给新前台加代理，继续使用既存共享后台 | 仍超时 | 前台设置没有覆盖实际请求处理路径 |
| 检查旧后台环境 | 未设置相应代理变量 | 找到前后台环境差异 |
| 使用继承代理环境的独立后台 | TUI 完成初始化 | 绕开旧后台后真实启动目标恢复 |

这里的通用原理是：进程有自己的环境。启动子进程时可向其传递环境，但后来修改 Shell 或新前台的变量，不会自动修改一个已经运行的后台进程。

```text
旧后台：启动时没有代理 → 后来仍保留自己的环境
新前台：本次设置代理 → 若复用旧后台，请求仍可能由旧环境处理
新独立后台：由正确环境启动 → 可以获得本次传入的代理设置
```

本地报告记录的修复是为指定入口加入启动包装器，补充可用代理并默认使用独立后台；原版本保持不变。**这比网页阶段多出的结论是环境与后台复用路径，不是“已证明必须降级”。** 报告未定位直连究竟在哪一跳受阻，不能继续归因为某个 ISP、DNS 或防火墙。

证据边界：上述数值和验收来自本次读到的先前本机报告，本轮整理没有重跑诊断。报告验证了账号请求、HTTP、WebSocket、TUI 启动与退出；没有提交模型问答，因此不能记为全部业务功能已验证，更不能据此认定用户已独立掌握排错。

### 4. 可复用的一行实验记录

| 假设 | 改变项 | 保持项 | 观察 | 结论与限制 |
| --- | --- | --- | --- | --- |
| 请求实际由未配置代理的旧后台处理 | 改为新独立后台 | 尽量保持版本、账号、目录、代理出口一致 | 启动成功／失败及对应日志 | 成功支持后台路径假设；仍需区分后台状态等伴随变化 |
