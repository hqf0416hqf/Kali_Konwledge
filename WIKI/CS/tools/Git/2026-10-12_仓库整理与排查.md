日期：2026-10-12。本文记录整理方案及自查方法；是否已经同步 GitHub，以 `git ls-remote --heads origin` 的实际输出为准。

目标是一个仓库管理 RAW、WIKI 和 .obsidian；本地与 GitHub 各保留 main，远程名为 origin。当前磁盘文件作为最终内容，AGENTS.md 和 readme.md 原样保留；远程初始化 README 保存在旧提交中，避免与本地 readme.md 产生大小写重名。旧提交通过整合提交的父提交保持可访问。历史里的分叉不会被抹掉；一个分支不等于历史只能是一条直线。

本次排查结果属于事实核查；以下教学解释和维护建议属于系统补充，未验证的理解不记为掌握。

## 二、学习路线

1. 判断自己操作哪个仓库，读懂工作区、暂存区、提交、分支和 HEAD。
2. 学会看提交图，理解分支名称只是指向提交的可移动引用。
3. 区分 main、origin、origin/main，判断 ahead / behind 与 push 拒绝。
4. 在临时练习仓库里新建分支、合并并解决真实文本冲突。
5. 学会撤销与恢复，最后补充 worktree、子模块和嵌套仓库。

当前仅提供知识地图与第一轮练习，尚未验证掌握程度。

## 三、第一套完整排查方法

先问五个问题：我在哪个仓库？文件改动是否提交？当前指向哪条分支？双方有哪些提交？远程地址是否正确？

```bash
git rev-parse --show-toplevel
git status -sb
git branch -avv
git log --graph --decorate --oneline --all -30
git remote -v
```

在统一后的仓库中，即使进入 WIKI/CS，`git rev-parse --show-toplevel` 也应返回外层 Kali_knowldge。查看较简洁的主线：`git timeline`；查看完整关系：`git overview`。

`M` 是修改，`D` 是删除，`??` 是尚未跟踪；简短状态的第一列是暂存区变化，第二列是工作区变化。普通编辑只改变工作区；`git add 文件` 把准备提交的内容放进暂存区；`git commit` 保存暂存区快照，并在普通分支状态下推进当前分支；`git push` 把已有提交发送给远程。

**例子**：编辑 WIKI/CS/tools/Git/Git.md 后，`git status -sb` 显示 main 和该文件的 M。此时只是 main 对应工作目录里的文件改了，尚未产生新提交，也没有新分支。

**独立练习**：看到 `## main...origin/main [ahead 1]`，下一行 ` M WIKI/CS/tools/Git/Git.md`。此时有几个本地未推送提交？该文件最新修改是否一定包含在那个提交中？只执行 push 是否能上传这次尚未暂存的修改？请解释理由。

## 四、日常记录流程

工作区干净且准备开始编辑时，可先 `git pull --ff-only`。如果拒绝，先检查，不要随意强制操作。完成一批笔记后：

```bash
git status -sb
git diff
git add RAW/具体文件.md WIKI/具体文件.md
git diff --cached
git commit -m "补充某个主题的学习笔记"
git push
```

以上路径是示意，要替换成实际文件。需要一次提交所有修改时，可在确认 `git status` 全部内容后使用 `git add -A`，它也会暂存删除。

## 五、遇到分叉和冲突时先分类

| 现象 | 先看什么 | 含义 |
| --- | --- | --- |
| 文件有 M / ?? | git status、git diff | 工作区变动，不等于分支冲突 |
| ahead / behind | fetch 后看提交图 | 本地与远程的提交关系 |
| non-fast-forward | git fetch origin，再看提交图 | 远程历史不能被本次普通推送直接推进；不等于已经发生文本冲突 |
| CONFLICT / UU | git status、git diff --name-only --diff-filter=U | 合并过程出现待解决的文件冲突 |
| unrelated histories | 仓库根目录、远程地址、根提交 | 双方可能是分别初始化的历史，需要确认是否应该整合 |
| 同一个目录出现两套分支 | git rev-parse --show-toplevel | 可能进入了嵌套仓库 |

`git fetch origin` 更新本地对远程历史的认识，不会直接把远程内容合并进工作区。`origin/main` 是本地保存的远程分支位置，不是实时联网指针。

冲突实操将在独立练习仓库完成：先提交干净的起点，再让两个分支修改同一行，执行 merge，检查冲突标记，按真实需求编辑最终文本，`git add` 后 `git commit`。不继续合并时可用 `git merge --abort`；开始前保留干净起点，避免已有改动让恢复复杂化。

不要把“删除分支”当作“解决文本冲突”；分支是历史引用，冲突需要决定最终文件应该是什么内容。

## 六、如何确认结构正常

```bash
git branch --list                  # 仅 main
git ls-remote --heads origin        # 仅 refs/heads/main
git status -sb                     # main 跟踪 origin/main
git worktree list                  # 仅当前工作目录
git ls-files --stage WIKI           # 文件逐个记录，无 160000 gitlink
```

Git 不记录空目录；这次保留本机空目录，但要让空目录出现在以后克隆的仓库中，需要有意放置 .gitkeep 等占位文件。

## 七、后期维护约定

- 本知识库目前只在 main 上维护；分支和冲突实验放在独立的临时练习仓库中。
- RAW 由 AI 按你的请求辅助整理，WIKI 主要由你维护；AI 修改 WIKI 时遵守你指定的范围。
- 在 RAW、WIKI 等子目录中不要再次运行 git init，不要移动或手工拼接 .git。
- 同一批文件只交给一个终端或助手执行 Git 结构变更，避免同时切换分支、提交或整理元数据。
- 开始编辑前，确认工作区干净，再 git pull --ff-only；结束时检查、暂存、提交、推送。
- git fetch 后的 origin/main 才反映最近读到的远程状态；网络失败时不要根据旧缓存断言已经同步。
- 遇到分叉先保存手头改动，git fetch 后读图，再决定合并；不要用强制推送作为默认排错方式。
- 本次仓库恢复材料保存在仓库旁边的 Kali_knowldge_git_recovery_时间戳 目录中，不纳入知识库 Git 提交。
