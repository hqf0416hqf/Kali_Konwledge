## 1. 为什么你会觉得毫无思路

这次问题同时跨过了几组知识：

| 知识组 | 本次对应的东西 |
|---|---|
| Shell | `type`、`PATH`、别名、环境变量、引号 |
| 程序安装 | 两个 `codex` 入口、不同版本、符号链接 |
| OS | 进程、继承的环境、文件权限、Socket、等待 |
| 网络 | 本地代理、域名、TCP、TLS、HTTP |
| 应用实现 | 账号读取、工作区发现、内部超时 |
| 工程诊断 | 日志、对照实验、版本回归、恢复与验证 |

如果这些连接还没建立，就算每个名词单独见过，也很难自己选择下一步。

别人直接给出长命令，还隐含着几层判断：

1. 他认为故障可能位于某一层。
2. 他选择一个工具观察这一层。
3. 他知道怎样解释工具的输出。
4. 他根据输出决定下一步。

你只看到第 2 步，就会感觉整个过程像猜谜。

以后每条诊断命令都先回答这五个问题：

| 问题 | 示例 |
|---|---|
| 要验证什么？ | 终端是否调用了另一份程序？ |
| 改变什么条件？ | 只把命令名换成绝对路径 |
| 保持什么不变？ | 账号、节点、目录、其他环境尽量相同 |
| 什么结果支持假设？ | 一个入口稳定失败，另一个稳定成功 |
| 结果有什么局限？ | 两个入口还可能有包装脚本和环境差异 |

你不需要一开始就知道根因；需要的是知道下一次实验如何增加信息。

## 2. 先判断：究竟失败在什么阶段

不要一看到“联网软件不能用”，就先认定是网络问题。

| 阶段 | 常见表现 | 优先检查 |
|---|---|---|
| Shell 查找命令 | `command not found` | 安装位置、`PATH`、别名、当前 Shell |
| OS 启动程序 | `Permission denied`、加载器或动态库错误 | 文件权限、架构、解释器、运行库 |
| 程序本地初始化 | 配置解析失败、数据库锁、读取文件失败 | 配置、路径、权限、残留进程、磁盘 |
| 连接远程服务 | 解析失败、连接拒绝、TLS 错误、超时 | 网络路径、代理、DNS、证书 |
| 远端身份与业务 | 401、403、账号／工作区错误 | 具体接口、身份、权限、客户端兼容 |
| 界面已启动，任务失败 | 可以进入界面，发送任务后报错 | 实际任务接口、模型访问、流式连接等 |

本次属于：**程序已经执行，终端界面初始化期间的 `account/read` 失败。**

这不同于命令不存在，也不同于已经进入聊天、但模型不回复。

### “突然不能用”为什么会发生

运行结果不只由程序文件决定，还受以下条件影响：

| 条件 | 即使你没有主动修改，也可能发生的变化 |
|---|---|
| 程序入口与版本 | 安装器更新、Shell 启动配置改变、切换 Node 环境 |
| 运行环境 | 换了终端、编辑器、工作目录或继承的环境变量 |
| 网络 | DNS、代理节点、出口、路由、网络限制变化 |
| 身份状态 | 凭据过期、刷新、账号／工作区权限变化 |
| 服务端 | 发布、接口变化、服务异常 |
| 本地资源 | 磁盘满、锁、权限、系统时间变化 |

**突然发生，只能说明某些条件变了；不自动说明“我操作错了”或“软件一定坏了”。**

## 3. 知识地图：一次联网请求涉及谁

| 对象 | 在哪里／是什么 | 负责什么 |
|---|---|---|
| 终端模拟器 | 用户态程序 | 显示文字、接收键盘输入 |
| Shell | 用户态程序，例如 Bash、Zsh | 解释命令、展开变量、查找和启动程序 |
| CLI 客户端 | 用户态程序，例如 Codex、curl | 读取配置、构造请求、处理响应 |
| 网络库 | 客户端使用的软件组件 | 连接、加密、HTTP 等协议处理 |
| Socket | OS 提供的通信接口／对象 | 让程序通过系统调用发送、接收数据 |
| 内核网络栈 | 内核软件 | 路由、TCP/IP、缓冲、与驱动配合 |
| 网卡与网络设备 | 硬件及其控制逻辑 | 实际传输数据 |
| 本地代理 | 另一份用户态程序 | 接收客户端请求，并按规则建立后续连接 |
| 远端接入与业务服务 | 远程机器上的软件 | 处理流量、认证、工作区发现与任务 |

CPU 执行这些软件指令，内存保存代码、数据和网络缓冲。网络库与代理不是某个专用 CPU 部件。

### 与今天学过的进程、内核如何连接

客户端可能执行创建 Socket、连接、等待和收发数据的系统调用。具体调用组合随实现不同。

- 建立连接、等待响应时，任务可能睡眠等待事件，CPU 可以运行其他任务。
- 内核收到相关事件后，等待的任务可能被唤醒，随后继续执行用户态代码。
- 程序说“超时”，通常表示软件设定的某个等待期限到了，不是 CPU 时钟坏了。
- TLS 和 HTTP 的许多处理在用户态软件中完成；不能把所有协议处理都归给内核。
- Socket 是一种访问 OS 网络能力的接口；PCB 是任务管理结构，二者用途不同。

### 两个名字相似、但层次不同的“路由”

| 名称 | 含义 |
|---|---|
| IP 路由 | 数据包经哪个网络接口、网关到达目标 |
| 工作区路由发现 | 应用为了处理账号／工作区请求，确定相应服务路径或目标的业务步骤 |

`workspace routing discovery` 是应用语义，不能直接翻译成“Linux 的 IP 路由表坏了”。仅凭错误文字也不能确定这个业务步骤内部究竟卡在哪里。

## 4. 先把“我到底执行了谁”搞清楚

### 4.1 命令名不等于某一个固定文件

输入：

```bash
codex
```

Shell 需要先解释这个名字。它可能对应别名、函数、内建命令或外部程序。具体查找规则和命令缓存行为取决于 Shell。

如果最后查找外部程序，`PATH` 会参与搜索。执行一个带路径的名字，通常就不需要再按 `PATH` 搜索这个程序名。

### 4.2 `type`：检查 Shell 怎样解释名字

```bash
type codex
type -a codex
```

| 命令 | 目的 | 是否修改设置 |
|---|---|---|
| `type codex` | 查看当前 Shell 如何解释 `codex` | 否 |
| `type -a codex` | 查看所有可找到的匹配，包括适用的别名、函数和程序入口 | 否 |

本次用户提供过：

```text
codex 是 /home/kali/.local/bin/codex
codex 是 /home/kali/.nvm/versions/node/v24.16.0/bin/codex
codex 是 /home/kali/.local/bin/codex
```

它说明存在两个不同的可查找入口。同一路径重复出现，通常是 `PATH` 的目录重复，不能据此判断安装了三份。

### 4.3 `PATH`：搜索目录列表

```bash
printf '%s\n' "$PATH"
```

Linux 上，目录之间通常用冒号分隔。输出很长时，可以这样逐行看：

```bash
printf '%s\n' "$PATH" | tr ':' '\n'
```

这里只是格式化输出，不会改变 `PATH`。

目录靠前，通常意味着该目录的同名外部程序优先，但仍要考虑别名、函数和 Shell 的具体查找机制。

### 4.4 绝对路径、符号链接、版本分别回答不同问题

```bash
readlink -f /home/kali/.local/bin/codex
/home/kali/.local/bin/codex --version
/home/kali/.nvm/versions/node/v24.16.0/bin/codex --version
```

| 检查 | 回答的问题 |
|---|---|
| 绝对路径启动 | 避开命令名查找差异，明确选择入口 |
| `readlink -f` | 符号链接最终解析到什么路径 |
| `--version` | 程序自己报告什么版本 |

绝对路径不能消除一切差异：入口还可能是脚本，依赖其他程序；程序仍会读取环境、配置和工作目录。

同一个版本号也不保证二进制、打包方式和启动包装完全相同。进阶比较可以对最终文件计算 `sha256sum`，但这不是每次排错的第一步。

### 4.5 这里为什么值得先查

如果你测试的是 A，却把结果归给 B，就会把后续所有判断带偏。Python、Node、Git、编译器等同名多版本问题都适用这个思路。

Shell 内建行为可以在 Bash 中使用 `help type`、`help alias`、`help export` 查询；Zsh 使用自己的帮助和手册。[S1]

## 5. 环境变量：为什么两个终端表现不同

### 5.1 它不是系统全局唯一的一张表

进程有自己的环境。父进程启动子进程时，会提供一份环境；子进程得到后，不会因为你后来修改另一个终端的变量而自动同步。

因此：

- 终端 A 设置了代理，不代表已打开的终端 B 也有。
- 浏览器能用，不代表终端继承了浏览器的代理设置。
- 编辑器里启动的 CLI，可能继承编辑器启动时的旧环境。
- 改了启动配置文件，不代表已经运行的进程立即变化。

### 5.2 三种写法，作用范围不同

| 写法 | 含义 | 持久性 |
|---|---|---|
| `name=value` | 设置当前 Shell 的变量；是否已导出还取决于该变量原有属性 | 通常限当前 Shell |
| `export name=value` | 设置并导出，使之后启动的子进程获得它 | 不自动写入配置文件 |
| `NAME=value command` | 为这次命令设置环境值 | 适合临时实验 |

例如本次：

```bash
RUST_LOG=debug /home/kali/.local/bin/codex
```

是在这次运行中设置日志过滤级别，不是在修改 Shell 的永久配置。

### 5.3 常见代理变量

| 名称 | 常见用途 |
|---|---|
| `http_proxy` | HTTP 请求使用的代理 |
| `https_proxy` | HTTPS 请求使用的代理 |
| `ALL_PROXY` / `all_proxy` | 某些程序支持的通用代理设置 |
| `NO_PROXY` / `no_proxy` | 指定哪些目标不使用应用层代理 |

**是否识别大小写、优先级和例外语法，必须看具体程序。**例如 curl 出于安全原因，对 HTTP 代理变量只接受小写 `http_proxy`；不能把某个工具的规则套到所有程序。[S2]

先只检查变量名，避免误贴带密码的代理 URL：

```bash
printenv | cut -d= -f1 | grep -Ei '^(http_proxy|https_proxy|all_proxy|no_proxy)$'
```

它只能证明这些名字是否存在，不能证明其值正确。需要时在本机查看值，分享前遮掉用户名和密码。

没有这些变量，也不等于没有代理：系统流量可能被 TUN、透明转发等方式处理。

### 5.4 启动配置文件为什么会影响结果

| 情况 | 常见文件／行为 |
|---|---|
| Bash 交互式非登录 Shell | 常见读取 `~/.bashrc` |
| Bash 登录 Shell | 规则涉及 `/etc/profile` 和个人登录启动文件 |
| Zsh 交互式 Shell | 通常读取 `$ZDOTDIR/.zshrc`；未设置 `ZDOTDIR` 时通常在主目录 |
| GUI 程序、服务、脚本 | 不一定读取你的交互式 Shell 配置 |

不要仅凭提示符样式判断 Shell。可以查看：

```bash
ps -p $$ -o comm=
```

`$SHELL` 通常反映配置的登录 Shell，不保证就是此刻正在运行的 Shell。

`source 文件` 会在当前 Shell 执行文件内容，可能包含更多副作用；不是单纯“刷新一下”。修改后开一个新终端验证，也是一种选择。Zsh 的启动文件规则见 [S3]。

## 6. 网络知识地图：从地址到业务响应

本节以常见的 TCP + TLS + HTTPS 连接为例。HTTP/3 使用 QUIC/UDP，不能把所有联网方式都硬套成 TCP。

### 6.1 URL：你究竟访问哪个服务

以这个虚构示例拆解：

```text
https://api.example.com:443/v1/account?refresh=false
```

| 部分 | 含义 |
|---|---|
| `https` | 使用的 URL 方案 |
| `api.example.com` | 主机名，可能需要解析到 IP |
| `443` | 端口；HTTPS 常见默认端口 |
| `/v1/account` | 资源路径／接口路径 |
| `refresh=false` | 查询参数 |

这个地址只是教学示例，不是本次 Codex 的真实内部接口。

**同一个域名的首页和账号 API，是不同请求。**首页能通，不能证明所有接口都能通。

### 6.2 IP、端口、域名

| 概念 | 解决什么问题 | 注意 |
|---|---|---|
| IP | 网络层面的寻址 | 一个服务可能有多个 IP，IP 也可能由多个服务共享 |
| 端口 | 区分传输端点 | 端口号不保证固定对应某个进程或业务 |
| 域名 | 用名字定位服务 | 解析结果可能随网络、时间、CDN 改变 |
| DNS | 把名字转换成相应记录等 | 不等于检查服务是否正常 |

`127.0.0.1` 是本机回环地址。本次 `127.0.0.1:7897` 指的是本机代理入口，不是 OpenAI 服务器。

### 6.3 DNS：名字能否解析

只读检查示例：

```bash
getent ahosts chatgpt.com
```

它通过系统配置的主机名解析机制查询，不一定只是直接问 DNS；例如可能涉及 `/etc/hosts` 等。

有 `resolvectl` 且系统使用相应解析服务时，也可检查：

```bash
resolvectl query chatgpt.com
```

**使用代理时，目标域名可能由代理侧解析。**所以本机解析成功／失败，未必代表应用这条代理路径上的解析结果。

### 6.4 TCP：有没有建立连接

常见错误：

| 现象 | 可以考虑什么 | 不能直接断言什么 |
|---|---|---|
| `Connection refused` | 目标或中间设备主动拒绝；端口未监听、规则拒绝等 | 不一定是账号问题 |
| 连接超时 | 网络路径丢弃、出口、目标不响应等 | 不一定是 DNS 错 |
| 连接成功 | 到这个端点的传输连接建立了 | 不代表 TLS、认证和业务成功 |
| `Connection reset` | 对端或中间路径重置连接 | 不能单凭这一句确定是谁重置、为何重置 |

如果客户端连的是本地代理，TCP 成功首先证明的是到本地代理这一段。

### 6.5 TLS：建立加密连接并验证身份

HTTPS 常使用 TLS 保护通信。理解三点即可：

1. TLS 握手协商加密参数等。
2. 证书验证用于检查所连接服务的身份与信任关系。
3. 加密连接成功，不等于业务授权通过。

证书错误可能涉及：系统时间不对、证书链不被信任、主机名不匹配、代理或组织网络使用私有 CA 等。TLS 原理参考 [S4]。

`using system root certificates` 只是“使用系统根证书”的说明；只有出现相应验证失败，才有证据沿证书方向排查。

不应把 `curl -k`／`--insecure` 当作默认修复：它会放弃重要的服务器证书验证。即使忽略验证后请求能走通，也只是提供了一个诊断线索，未修复信任问题。

### 6.6 HTTP：对方怎样回应这个请求

| 状态 | 入门含义 | 排查注意 |
|---|---|---|
| `200` | HTTP 层通常表示成功 | 仍要确认响应内容、目标身份和业务结果 |
| `3xx` | 重定向 | 看目标位置；是否跟随会改变测试范围 |
| `401` | 目标资源需要有效认证 | 核对具体请求是否带了正确凭据 |
| `403` | 请求被理解，但被拒绝执行 | 不足以单独证明账号封禁、令牌失效或 IP 被封 |
| `404` | 未找到资源，或服务不愿披露其存在 | 核对路径、版本和身份，不能只改网络 |
| `407` | 代理要求认证 | 与目标服务的登录是两回事 |
| `429` | 请求受到限流 | 检查响应说明和重试策略，不要连续猛重试 |
| `5xx` | 服务端／网关处理异常 | 具体原因仍需看响应和服务链路 |

CONNECT 的语义和标准 HTTP 状态码见 [S5]；429 的定义另见 [S6]。注意，有些系统还会返回非标准状态码，必须查该系统的语义。

### 6.7 认证、授权、业务成功不是同一回事

| 层次 | 问题 |
|---|---|
| 凭据存在 | 本机是否存有登录信息？ |
| 身份认证 | 服务端是否认可当前凭据？ |
| 权限检查 | 这个身份是否能访问相应工作区／功能？ |
| 业务完成 | 请求对应的工作是否实际完成？ |

因此，“显示已登录”不能独立证明工作区请求成功。“HTTP 200”也不保证业务一定成功；有些系统会在响应正文中报告业务错误。

### 6.8 “超时”也有不同的边界

| 时间限制 | 可能覆盖什么 |
|---|---|
| 连接建立超时 | 解析、连接、相应握手等建立阶段，依工具定义 |
| 响应／读取超时 | 已连接后等待相应响应或数据 |
| 整次请求超时 | 一次请求的总预算 |
| 业务操作超时 | 可能包含排队、本地状态读取、多个请求、重试等 |

外层业务有 15 秒预算时，内部某一步变慢，就可能让整个业务超时；不一定有单个网络请求恰好卡满 15 秒。重试还会消耗剩余预算。

所以要先问“谁设置的时间限制、限制的范围是什么”，不要把增加任意一个 timeout 参数当成通用修复。

## 7. 代理：为什么本地能连上，远端仍可能失败

### 7.1 先区分三个对象

| 对象 | 本次例子／含义 |
|---|---|
| 本地代理入口 | `127.0.0.1:7897`，客户端先连接它 |
| 代理节点／出口 | 代理软件选择的后续网络路径 |
| 目标服务 | `chatgpt.com` 及实际请求的相应服务 |

本地代理端口接受连接，只证明入口有响应；后续还涉及节点、域名解析、上游连接、目标处理等。

### 7.2 HTTPS 经 HTTP 代理的常见方式

在本案例使用的 HTTP 代理方式下，客户端通常先向代理发出 CONNECT，请求建立到目标的隧道；隧道建立后再进行目标 TLS 握手，然后发送 HTTPS 请求。

所以输出里可以同时出现两种状态：

| 字段 | 谁的回应 |
|---|---|
| `CONNECT=200` | 代理对建立隧道的回应 |
| `HTTP=403` | 随后获取到的 HTTP 资源响应 |

它们对应不同阶段，不冲突。

代理地址写成 `http://127.0.0.1:7897`，不代表目标网站的 HTTPS 被自动改成明文；前者描述的是客户端与代理交互所使用的方案。是否存在 TLS 检查或代理终止 TLS，还要看具体配置，不能只从这一个字符串判断。

### 7.3 HTTP 代理、SOCKS 和 TUN

| 类型 | 入门理解 | 排错重点 |
|---|---|---|
| HTTP 代理 | 应用通过 HTTP 代理机制转发／建隧道 | 应用是否支持、代理端口和认证是否正确 |
| SOCKS 代理 | 应用通过 SOCKS 协议请求连接 | 协议、端口、目标解析由谁负责 |
| TUN 等系统级流量接管 | 流量通过虚拟网络接口等机制处理 | 路由、DNS、分流、是否仍有其他代理叠加 |

curl 中，`socks5://` 和 `socks5h://` 在目标主机名由哪一侧解析上有区别；后者请求由代理解析。只有确认该端口支持 SOCKS 时才用，不能随意更换协议前缀。[S7]

### 7.4 “全局代理”也要看选中了什么出口

全局、规则、直连是代理软件的策略概念。全局模式的具体行为取决于软件及当前选择，不能只看按钮名称就保证每个程序、每条连接都走某个节点。

一个有用的实验应记录：

- 程序入口和版本。
- 代理模式、选中的策略／节点。
- 本地端口和应用层代理变量。
- 是否存在 TUN 或其他转发。
- 成功／失败及时间。

### 7.5 为什么换热点不一定等于换出口

如果换成手机热点后仍使用同一个代理节点，对目标服务来说，出口可能仍相同。

同样，换一个节点名字也不保证完全独立：节点可能共享出口、上游或分流规则。因此“换节点无效”是证据，但不能彻底排除所有网络因素。

## 8. 把本次 curl 命令拆开看

### 8.1 完整命令

下面的 `7897` 来自本次用户日志，不是所有电脑通用的端口。其他场景应使用实际端口。

```bash
curl -x http://127.0.0.1:7897 --noproxy "" \
  --connect-timeout 10 --max-time 20 \
  -sS -o /dev/null \
  -w 'HTTP=%{http_code} CONNECT=%{http_connect} TLS=%{time_appconnect}s TOTAL=%{time_total}s\n' \
  https://chatgpt.com/
```

**实验目的：检查经这个代理的一次首页 HTTPS 请求进行到了哪里。它不携带 ChatGPT 登录凭据，不是工作区 API 测试。**

### 8.2 每一段的含义

| 片段 | 含义 |
|---|---|
| `curl` | 发起请求的程序 |
| `-x http://127.0.0.1:7897` | 明确指定应用层代理 |
| `--noproxy ""` | 清空 curl 的不走代理目标列表，避免例外规则影响本次测试 |
| `--connect-timeout 10` | 限制连接建立阶段的等待时间；涉及的建立阶段包括相应 DNS／TCP／TLS 等，不只是 TCP |
| `--max-time 20` | 限制整次传输的总时间 |
| `-sS` | 安静显示，但保留错误消息 |
| `-o /dev/null` | 丢弃响应正文；不是没有接收正文 |
| `-w '…'` | 传输结束后，输出选定指标 |
| 最后一行 URL | 本次访问的目标资源 |

`--noproxy ""` 不会关闭 TUN，不会修改系统路由。`-o /dev/null` 也不等于关闭网络访问。命令行为以 curl 手册为准。[S8]

### 8.3 `%{…}` 和 Shell 的 `$…` 不一样

| 写法 | 通常由谁解释 |
|---|---|
| `$PATH`、`$codex_diag_dir` | Shell |
| `%{http_code}`、`%{time_total}` | curl 的 `--write-out` |
| `\n` | 在这里由输出格式处理为换行 |

`-w` 的输出格式和变量语法见 [S9]。

### 8.4 你的真实输出怎样解读

```text
HTTP=403 CONNECT=200 TLS=1.562088s TOTAL=2.170753s
```

| 观察 | 合理结论 | 不能推出 |
|---|---|---|
| CONNECT 为 200 | 代理接受了建立隧道的请求 | 所有后续业务都正常 |
| TLS 指标约 1.56 秒 | 在这次简单新连接测试中，约在该时刻完成 TLS 等握手阶段 | TLS 纯计算耗时恰好为 1.56 秒 |
| HTTP 为 403 | 收到了拒绝执行该资源请求的 HTTP 响应 | 账号一定失效；Codex 具体接口也返回 403 |
| 总耗时约 2.17 秒 | 这次请求在有限时间内结束 | Codex 的 15 秒超时由这次首页请求造成 |

**这些时间通常是自传输起点计的累计时间，不是各阶段独立耗时。**复杂场景中的重定向、连接复用等还会影响解读，不能机械相减后当成绝对根因。

### 8.5 HTTP 状态码与程序退出码是两回事

这是特别容易混淆的地方：

```bash
curl -sS -o /dev/null --connect-timeout 10 --max-time 20 -w 'HTTP=%{http_code}\n' https://example.com/
curl_result=$?
printf 'curl退出码=%s\n' "$curl_result"
```

`$?` 表示上一条命令的退出状态，所以要紧跟着保存，不能中间先执行别的命令。

curl 默认收到 HTTP 403，仍可能以退出码 0 结束：它成功完成了一次获得拒绝响应的传输。使用 `--fail` 等选项会改变这种行为。[S10]

| 数字 | 属于哪一层 |
|---|---|
| HTTP `403` | HTTP 响应状态 |
| curl `28` | curl 对超时的退出码 |
| JSON-RPC `-32603` | 应用内部 RPC 协议的内部错误类别 |
| OS 的 `EACCES`／`ECONNREFUSED` | 系统调用／底层操作的错误信息 |

这些数字不能互相替代解释。没有拿到 HTTP 状态时，curl 可能显示 `HTTP=000`；000 不是服务器发回的标准 HTTP 状态码。

### 8.6 常见 curl 退出码速查

| 退出码 | 常见含义 | 下一步 |
|---|---|---|
| 5 | 代理主机名无法解析 | 核对代理主机名及其解析路径 |
| 6 | 目标主机名无法解析 | 核对域名与实际使用的解析路径 |
| 7 | 连接失败 | 核对连接对象、监听端口及网络路径 |
| 22 | 启用相关失败选项时遇到 HTTP 错误 | 查看实际 HTTP 状态及响应 |
| 28 | 达到超时限制 | 判断超时发生阶段与预算 |
| 35 | TLS 连接／握手错误 | 查看完整错误，检查协议和连接路径 |
| 60 | 证书验证失败 | 检查时间、名称、证书链和信任来源 |

退出码速查仅提供方向，完整消息和具体版本仍然重要。[S10]

## 9. 把本次日志命令拆开看

### 9.1 创建临时目录

```bash
codex_diag_dir=$(mktemp -d /tmp/codex-diag.XXXXXX)
printf '日志目录：%s\n' "$codex_diag_dir"
```

| 片段 | 含义 |
|---|---|
| `mktemp -d` | 创建一个唯一的临时目录 |
| `XXXXXX` | 由工具替换的随机部分，避免重名 |
| `$(…)` | 执行其中命令，把标准输出用于外层命令 |
| `codex_diag_dir=…` | 把得到的目录路径保存为变量 |
| `"$codex_diag_dir"` | 展开变量；双引号保留包含空格等情况的参数边界 |
| `printf` | 按格式输出文字 |

它会创建临时目录，不是完全没有文件改动；但不会因此清空 Codex 的原始配置。`/tmp` 可能被清理，不适合长期存储唯一的诊断证据。

`codex_diag_dir` 只在定义它的 Shell 中可直接使用。换终端后，若想读取已有日志，应重新把变量设置为那个实际存在的目录，或直接使用完整日志路径；重新运行 `mktemp` 会创建另一个目录。

### 9.2 为一次启动启用调试日志

```bash
RUST_LOG=debug /home/kali/.local/bin/codex -c "log_dir=\"$codex_diag_dir\""
```

分成三部分：

1. `RUST_LOG=debug`：给这次运行设置日志过滤级别。
2. 完整路径：明确启动本次要测试的客户端。
3. `-c`：提供本次配置覆盖，把日志目录指定到临时目录。

最后一段看起来复杂，是因为同时涉及两层语法：外层 Shell 要展开目录变量，内层配置中的路径还需要作为字符串。

不必把这段转义当成排错入门的先修条件。可以先理解效果，再通过简单 Shell 实验练习引号。Codex 的日志环境变量、显式 `log_dir` 行为见 [S11]。

调试日志可能包含私人路径、请求标识或敏感内容；只摘取必要片段，不上传认证文件。

### 9.3 筛选日志，不是在执行日志内容

```bash
rg -n -i 'workspace|routing|timeout|error|warn' "$codex_diag_dir/codex-tui.log" | tail -n 60
```

| 片段 | 含义 |
|---|---|
| `rg` | 搜索文本 |
| `-n` | 显示匹配所在行号 |
| `-i` | 忽略大小写 |
| `'a|b'` | 正则表达式：匹配 a 或 b |
| 日志路径 | 要搜索的文件 |
| `|` | 把左边命令的标准输出接给右边 |
| `tail -n 60` | 只看最后 60 行 |

没有 `rg` 时，本例可改用 `grep -nEi`。正则表达式引号内的 `|` 是匹配规则，命令之间的 `|` 是 Shell 管道，位置决定语义。

**筛选会丢上下文。**看到重要行号后，可以回看附近：

```bash
sed -n '220,250p' "$codex_diag_dir/codex-tui.log"
```

这里的行号只是示例，要按自己的实际日志调整。

### 9.4 标准输出、标准错误、退出码

| 对象 | 含义 |
|---|---|
| stdout，文件描述符 1 | 普通输出通道 |
| stderr，文件描述符 2 | 常用于错误和诊断输出 |
| 退出码 | 程序结束时交给调用者的状态 |

在本机创建测试文件后，可以尝试：

```bash
ls /a-path-that-does-not-exist 2> /tmp/cli-error-demo.txt
ls_result=$?
printf '退出码=%s\n' "$ls_result"
cat /tmp/cli-error-demo.txt
```

`2>` 把错误通道写入文件；它不是修复错误。文件会被创建或覆盖，所以示例只使用专门的临时演示文件。

管道末尾看到的退出码也未必是左边程序的退出码。进阶时再学习 Bash 的 `PIPESTATUS`、Zsh 的 `pipestatus` 和 `pipefail`，不要先背一串选项。

### 9.5 一行日志的阅读顺序

以本次日志为例：

```text
2026-10-19T13:49:32.232281Z DEBUG ... connected to 127.0.0.1:7897
```

先看时间、级别、模块、事件内容，再看关联请求。

| 字段 | 意义 |
|---|---|
| `Z` | UTC 时间；该条换算为北京时间是 21:49:32 左右 |
| `DEBUG` | 调试级别，不等于故障 |
| `INFO` | 运行信息，不等于一切正常 |
| `WARN` | 值得关注，不保证是根因 |
| `ERROR` | 报告失败，仍需定位触发原因 |
| `account/read`、请求 ID | 帮助把不同线程／请求的日志关联起来 |

“最后一条警告”可能只是失败后的清理结果。并发日志还可能交错，时间挨着不代表一定存在因果关系。

日志里的 `time.busy`／`time.idle` 还可能是跟踪 span 的活动时间统计，不是 CPU 利用率或精确的系统调度统计，不能把它直接解释成“CPU 忙了几毫秒、睡了几秒”。

## 10. 通用排错流程：每一步都要增加信息

### 第一步：把现象写成可复现事实

不要只写“Codex 坏了”，改成：

> 在某个终端、某个目录、某个网络下，执行这个绝对路径的客户端，在进入终端界面前等待约 15 秒，报工作区发现超时。

记录五件事：版本、入口、完整错误、发生阶段、是否稳定复现。

### 第二步：先分层，再选工具

| 你的假设 | 优先观察 |
|---|---|
| 调用了另一份程序 | `type -a`、完整路径、版本、最终链接目标 |
| 读取了不同环境 | 当前 Shell、变量名与必要值、工作目录 |
| 配置／本地资源出错 | 程序日志、权限、磁盘、锁、相关配置 |
| 本地代理未运行 | Socket 监听、连接拒绝、代理进程 |
| 上游连接失败 | 指定代理的请求、代理连接日志 |
| 认证或业务失败 | 具体接口的响应、程序日志、最小业务验证 |
| 客户端版本差异 | 同环境下切换明确版本并复验 |

工具是用来回答问题的，不是一次把所有工具都运行一遍。

### 第三步：优先选择信息量高、代价小的实验

本次已有两个安装入口，比较它们的版本和启动结果成本很低，应该较早进行，而不应在缺少新证据时反复换节点、反复登录。

每个测试选取决于：

- 能否区分至少两个主要假设。
- 是否可重复。
- 是否容易恢复。
- 是否会引入额外变量。

### 第四步：尽量一次只改一个条件

理想的版本对照：

| 条件 | A | B |
|---|---|---|
| 目录 | 同一目录 | 同一目录 |
| 账号与配置 | 同一组 | 同一组 |
| 代理模式／节点 | 同一组 | 同一组 |
| 时间 | 尽量接近 | 尽量接近 |
| 唯一主要变化 | 客户端 A | 客户端 B |

如果一次同时换版本、节点、账号并删配置，即使恢复也难知道哪个变化有效。

### 第五步：区分观察、推断、根因

| 等级 | 本次例子 |
|---|---|
| 观察事实 | 用户报告不同版本的另一份客户端能用 |
| 受支持的推断 | 入口／版本相关差异应优先调查 |
| 待验证的解释 | 新客户端触发了不同工作区发现路径或超时行为 |
| 尚未确认的根因 | 具体代码缺陷、触发条件及服务端交互细节 |

同一份程序前后偶然恢复，也可能与时间和网络波动有关。条件允许时重复 A、B、A、B，能提高判断可信度；不要为了“绝对证明”无限测试。

### 第六步：恢复后验证真实目标

恢复有多个层次：

1. `--version` 正常。
2. 终端界面正常启动。
3. 能完成一个最小实际请求。
4. 新开终端后，普通命令仍调用正确入口。

到达第 2 层，不自动等于第 3、4 层也已经验证。

### 第七步：记录停止条件

业务已恢复、主要证据已保存，且继续深挖的收益不高时，可以先结束诊断。保留“当前已知”和“尚未确认”，不强行编一个完整根因。

| 项目 | 已有记录 |
|---|---|

| 默认入口 | `/home/kali/.local/bin/codex` |

### 11.2 报错的层级

```text
Error:
  account/read failed during TUI bootstrap:
    account/read failed:
      workspace routing discovery timed out
      (code -32603)
```

| 部分 | 可以理解为 |
|---|---|
| TUI bootstrap | 终端交互界面启动过程 |
| account/read | 内部账号读取操作／方法，不是已经确认的 HTTP URL |
| workspace routing discovery | 工作区路由发现业务步骤 |
| timed out | 这个步骤没有在允许的时间预算内完成 |
| -32603 | RPC 错误类别；不是 HTTP 状态码，具体原因仍看消息和日志 |

这段错误说明失败发生在哪里，并未直接给出最底层根因。

### 11.3 日志能支持哪些结论

| 日志／观察 | 能支持 | 不能支持 |
|---|---|---|
| `connected to 127.0.0.1:7897` | 当次本地代理连接建立 | 目标业务成功；出口完全正常 |
| `pooling idle connection` | 网络库把连接放回可复用池等运行行为 | 工作区发现已成功 |
| `using system root certificates` | 当次使用系统信任证书来源 | 发生了证书错误 |
| `idle=15.0s` | 相应跟踪 span 记录了约 15 秒的非活动区间，操作整体接近这个时间量级 | CPU 恰好睡眠 15 秒；某次 TCP 或 TLS 恰好等待 15 秒 |
| `ab.chatgpt.com` 连接日志 | 还存在对该域名的连接尝试 | 它必定是账号读取根因 |
| 遥测退出超时 | 退出清理阶段另有等待未完成 | 遥测导致最初启动失败 |

### 11.4 为什么 curl 的 403 没有“破案”

curl 实验与 Codex 业务请求不同：

| 条件 | curl 首页测试 | Codex 工作区发现 |
|---|---|---|
| 客户端实现 | curl 及其依赖 | Codex 及其依赖 |
| 资源 | 首页 `/` | 具体内部请求未完整确认 |
| 登录信息 | 命令未携带 ChatGPT 登录信息 | 使用客户端的相应认证机制 |
| 请求头和行为 | curl 的请求行为 | 客户端实际行为 |
| 时间预算 | 实验设置总计 20 秒 | 日志中该操作约 15 秒 |

所以该实验提供了基础链路证据，却不是工作区接口的等价重现。程序不同，还可能带来 DNS、代理、TLS、HTTP 版本、超时及重试策略差异。

### 11.5 为什么客户端对照更有价值

同一台电脑上，一个明确入口失败，另一个不同版本可用，直接把“入口／版本／实现差异”提到了排查前列。

但还不能把结论写成：

> 已证明 Codex 0.163.0 在所有环境下都有同一个官方确认缺陷。

合理结论是：

> 当前用户环境中，默认入口的 0.163.0 出现工作区发现超时；另一份不同版本可用。故障与客户端相关差异有明显关联，具体触发条件及根因仍未确认。

网络与版本也可能相互作用：旧客户端走得通，不证明任何网络环节都不可能参与新客户端的失败。

### 11.6 本次可以改进的排查方式

1. 已知存在两个入口后，应更早完成版本对照。
2. 不应在缺少新证据时反复建议同一组网络／登录测试。
3. 给命令前应解释假设、观察对象和判断边界。
4. 首页请求只能作为基础测试，不能代替真实业务请求。
5. 用户已换节点、已重登录，应保留这个结果，后续按新证据推进。

排查没能第一步命中根因并不奇怪；真正要避免的是没有记录、没有区分度地重复操作。

## 12. 恢复可用入口，以及理解“临时修复”

### 12.1 当前已知可用入口

```bash
/home/kali/.nvm/versions/node/v24.16.0/bin/codex
```

这条路径来自本次用户环境，换电脑或切换 Node 版本后不能直接照搬。

### 12.2 当前终端设置别名

```bash
alias codex='/home/kali/.nvm/versions/node/v24.16.0/bin/codex'
type codex
codex --version
```

作用：普通输入 `codex` 时，明确选择可用入口。设置别名不卸载程序、不清空账号、不修复失败版本的内部问题。

撤销当前 Shell 的这个别名：

```bash
unalias codex
```

交互式别名通常不会像环境变量那样自动被普通子进程／非交互脚本继承；它不等于全系统统一入口。

### 12.3 持久化前先理解配置位置

若使用 Zsh，把那一行别名写到实际读取的交互启动文件，通常是 `~/.zshrc`；设置了 `ZDOTDIR` 时需使用对应位置。Bash 的普通交互终端通常使用 `~/.bashrc`，登录 Shell 还有自己的启动规则。

这是修改持久文件。修改前保留备份，避免反复追加重复行；新开终端后再次使用 `type codex` 和 `codex --version` 验证。

固定到 Node 版本目录是一种恢复手段。将来升级／卸载 Node 后该路径可能失效，届时应重新整理入口，而不是继续堆叠别名。

### 12.4 恢复、绕过、修复、根因分析

| 名称 | 本次对应的含义 |
|---|---|
| 恢复服务 | 现在能够继续使用 Codex |
| 绕过措施 | 选择另一份已验证可用的客户端 |
| 根因修复 | 修复失败实现、配置或触发条件，并重新验证 |
| 根因分析 | 解释为什么只有某个入口／版本失败 |

可以先恢复，再决定是否继续深入。不要把绕过措施写成已确认的根因补丁。

## 13. 工具箱：根据问题选择，不按顺序全部运行

### 13.1 本地入口与进程环境

| 命令 | 主要回答 | 边界 |
|---|---|---|
| `pwd` | 当前工作目录是什么 | 不等于所有配置的实际来源 |
| `type -a 程序名` | Shell 能找到哪些解释／入口 | 不证明入口是同一文件 |
| `readlink -f 路径` | 链接最终目标 | 目标还可能是包装脚本 |
| `程序 --version` | 自报版本 | 不验证远程业务 |
| `ps -p $$ -o comm=` | 当前 Shell 进程名字 | 包装层等环境仍需具体分析 |
| `date -Is` | 当前时间和时区偏移 | 需要对照可信时间才能判断准确性 |
| `df -h` | 文件系统空间概况 | 小文件很多时还可能要看 inode |
| `df -i` | inode 使用情况 | 与字节空间是两个指标 |

### 13.2 查看本地代理是否监听

```bash
ss -lntp 'sport = :7897'
```

| 参数 | 含义 |
|---|---|
| `-l` | 监听状态 |
| `-n` | 数字形式显示地址和端口 |
| `-t` | TCP Socket |
| `-p` | 尝试显示关联进程信息 |
| 过滤条件 | 只看本次端口 |

普通用户可能看不到其他用户的完整进程信息；没有进程名称，不等于没有监听。监听只证明入口存在，不证明代理上游可用。[S12]

### 13.3 基础网络与 DNS

```bash
ip -br address
ip route
getent ahosts chatgpt.com
```

分别查看接口地址概况、路由、系统名字解析结果。它们都是观察工具，不会自动修复连接。

| 工具／现象 | 常见误区 |
|---|---|
| `ping` 成功 | 不保证 HTTPS、代理和业务正常 |
| `ping` 失败 | 对方可能不回应 ICMP，不代表 HTTPS 一定失败 |
| `traceroute` 某跳不回应 | 路由器可能不回复探测，不等于那里必然断网 |
| 本机 DNS 正常 | 代理侧解析、应用自带解析仍可能不同 |
| 访问固定 IP | HTTPS 还涉及主机名、证书、SNI 和服务路由，不能简单替代域名请求 |

不要为了某个应用的工作区错误，未经证据就修改系统 DNS、清空路由或重置防火墙。

### 13.4 更细的 HTTP 观察

无凭据的基础请求可以用：

```bash
curl -v --connect-timeout 10 --max-time 20 https://example.com/ -o /dev/null
```

`-v` 显示更多连接和协议交互。它不能自动解释业务根因。若自行增加了认证头、Cookie 或带密码的代理地址，输出可能敏感，分享前必须检查。

`-I` 发的是 HEAD 请求，不保证和原程序的 GET／POST 有相同结果；`-L` 会跟随重定向，可能改变你实际测试的目标。诊断时要知道自己改变了请求的哪一部分。

### 13.5 strace：从应用日志深入到系统调用

仅在普通日志不足时考虑。以 Linux 上本次入口为例：

```bash
strace -f -tt -T -e trace=connect,getsockopt,poll,ppoll,epoll_wait \
  -o /tmp/codex-connect.strace /home/kali/.local/bin/codex
```

它创建或覆盖专门的跟踪文件，启动目标并记录选定系统调用；不需要为普通用户自己的进程默认加 `sudo`。

| 参数 | 作用 |
|---|---|
| `-f` | 跟踪子进程等 |
| `-tt` | 记录较细时间戳 |
| `-T` | 记录系统调用耗时 |
| `-e trace=…` | 限制观察范围 |
| `-o` | 将跟踪保存到指定文件 |

边界：跟踪会影响时序；这里的过滤不是完整网络行为记录。加密流量不会因为用了 strace 就自动变成可读业务内容。非阻塞 `connect` 返回 `EINPROGRESS` 常是正常的连接进行中状态，不能把每个非零返回都当成根因。[S13]

抓包、Wireshark／tcpdump、复杂路由和程序源码分析属于后续工具，不是现在必须一次学完的内容。

## 14. 五个小实验：把“照命令执行”变成“能预测结果”

每个实验都按“先预测、再运行、最后解释”进行。只在自己的临时目录中练习。

### 实验 A：相同命令名，两个入口

目标：理解为什么安装过程序，仍可能执行另一份。

```bash
demo_root=$(mktemp -d /tmp/cli-path-demo.XXXXXX)
mkdir -p "$demo_root/a" "$demo_root/b"
printf '#!/bin/sh\nprintf "version-A\\n"\n' > "$demo_root/a/demoapp"
printf '#!/bin/sh\nprintf "version-B\\n"\n' > "$demo_root/b/demoapp"
chmod u+x "$demo_root/a/demoapp" "$demo_root/b/demoapp"
env PATH="$demo_root/a:$demo_root/b:$PATH" sh -c 'command -v demoapp; demoapp'
env PATH="$demo_root/b:$demo_root/a:$PATH" sh -c 'command -v demoapp; demoapp'
```

预测：两次调用的名字相同，输出是否相同？

解释：只在这两个子进程中调整 `PATH`，不会修改当前 Shell 的永久设置。实验创建临时文件；没有访问远端服务。

### 实验 B：变量存在，不等于已导出

目标：理解子进程得到什么环境。

```bash
(
  unset CLI_DEMO_MARK
  CLI_DEMO_MARK=hello
  sh -c 'printf "未导出：%s\n" "${CLI_DEMO_MARK-未收到}"'
  export CLI_DEMO_MARK
  sh -c 'printf "已导出：%s\n" "${CLI_DEMO_MARK-未收到}"'
)
```

预测：两次子进程分别输出什么？

括号使整个实验在子 Shell 环境中完成，避免把这个变量残留在当前 Shell。

### 实验 C：HTTP 错误与 curl 退出码

需要 Python 3 和 curl。开启一个终端运行：

```bash
demo_http_root=$(mktemp -d /tmp/cli-http-demo.XXXXXX)
python3 -m http.server 8765 --bind 127.0.0.1 --directory "$demo_http_root"
```

如果端口被占用，换一个空闲端口，并同步修改后续 URL。这个服务只绑定本机回环地址，实验结束后按 `Ctrl+C` 停止。

在另一个终端执行：

```bash
curl --noproxy '*' -sS -o /dev/null -w 'HTTP=%{http_code}\n' http://127.0.0.1:8765/missing-file
curl_result=$?
printf '默认退出码=%s\n' "$curl_result"
curl --noproxy '*' --fail -sS -o /dev/null -w 'HTTP=%{http_code}\n' http://127.0.0.1:8765/missing-file
curl_result=$?
printf '启用fail后的退出码=%s\n' "$curl_result"
```

预测：两次都是 HTTP 404，程序退出码是否相同？

这个实验不依赖国外网络、账号或代理节点，适合单独理解两个错误层级。

### 实验 D：端口监听不等于业务成功

保持实验 C 的本地服务运行，在另一个终端执行：

```bash
ss -lnt 'sport = :8765'
curl --noproxy '*' -sS -o /dev/null -w 'HTTP=%{http_code}\n' http://127.0.0.1:8765/missing-file
```

预测：为什么端口在监听、请求也能完成，却返回 404？

对照本次案例：本地代理连上，只说明前面一部分正常，后面的资源处理仍可能失败。

### 实验 E：用自己的话写一份最小排错记录

不增加新命令。选择上面的任意实验，写下：

```text
目标：
实际现象：
我的假设：
只改变的条件：
保持不变的条件：
命令与关键输出：
这个输出证明：
这个输出不能证明：
下一步或停止条件：
```

能独立完成这个记录，比再记住十条命令更能说明你建立了排错思路。

## 16. 下次出错时，只拿这一页开始

### 16.1 先回答六个问题

1. 我要完成什么，具体卡在哪一步？
2. 完整错误是什么？属于 Shell、OS、网络库、HTTP 还是业务协议？
3. 实际运行哪个入口、哪个版本、什么目录和环境？
4. 最后一次正常是什么时候，此后哪些条件可能变化？不知道也如实记。
5. 哪个低成本实验最能区分当前的两个主要假设？
6. 什么结果算恢复，怎样验证？

### 16.2 每次只记一行实验

| 编号 | 假设 | 唯一主要变化 | 输出／结果 | 支持什么 | 仍不能说明什么 |
|---|---|---|---|---|---|
| 1 | 入口不同 | 改用已知另一完整路径 | 待填写 | 待填写 | 待填写 |
| 2 | 原节点路径有问题 | 只换节点 | 待填写 | 待填写 | 待填写 |
| 3 | 配置差异 | 受控地改变相关配置 | 待填写 | 待填写 | 待填写 |

不是要求把表全部做完。哪一个实验最有价值，就先做哪一个；有了结果再调整。

### 16.3 常见错误的第一反应

| 报错／现象 | 第一反应 |
|---|---|
| `command not found` | 查命令解释与入口，别先查 DNS |
| `Permission denied` | 先判断是本地文件权限还是远端响应 |
| `Could not resolve…` | 先确认解析的是目标还是代理，以及由谁解析 |
| `Connection refused` | 确认连谁、什么端口、是否监听 |
| TLS 证书错误 | 看时间、主机名、证书链和信任来源 |
| HTTP 401／403 | 看具体请求、凭据和响应，别直接宣布账号坏了 |
| 只有 timeout | 先找失败阶段和等待预算，别把“超时”当完整根因 |
| 一份版本能用另一份不能 | 优先保留成功入口，做受控的客户端差异检查 |

### 16.4 少做这些无区分度的动作

- 连续重试十次，却不记录每次条件。
- 看到联网软件报错就先重装。
- 同时换节点、换账号、改版本、删配置。
- 反复重新登录，却没有认证失败证据。
- 把 403、超时和证书错误统称为“网络不行”。
- 看到最后一条警告就认定根因。
- 为了“排除干扰”直接删除整份配置和凭据。
- 复制需要自己填写的端口／路径，却不确认实际值。

### 16.5 向别人求助的模板

```text
目标：我想启动……
环境：系统／Shell／客户端版本……
实际入口：……

```
